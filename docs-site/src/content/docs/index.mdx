## What this is

AgriBatch Pay tracks a **batch** — one crop, one season, one buyer — and the **farmer lots** inside it. Each lot records a farmer, a weight, a price and a grade. The platform totals them, records quality confirmation, and records the buyer funding and approving the settlement.

Every one of those steps is written twice: once to PostgreSQL, so the platform is usable, and once to a Soroban contract on Stellar testnet, so the record is not the platform's to rewrite.

<CardGrid stagger>
  <Card title="Built for the many-to-one case" icon="seti:folder">
    A coffee container is not one seller's crop. It is forty growers' sacks, weighed separately, graded separately, and paid from one wire. AgriBatch Pay keeps the lots separate all the way through settlement.
  </Card>
  <Card title="The arithmetic is on chain" icon="approve-check">
    Lot totals are summed by the contract, not by the app. A farmer checking their share is reading the same number the buyer approved against.
  </Card>
  <Card title="Live event stream" icon="rocket">
    Batch creation, lot registration, quality confirmation, funding and approval all push to a server-sent event stream, so a cooperative watching a settlement sees it move.
  </Card>
  <Card title="Two contracts, two jobs" icon="puzzle">
    A batch registry that owns the harvest record, and a payout vault that owns the money side. Separated so neither has to trust the other's storage.
  </Card>
</CardGrid>

<Aside type="caution" title="Read this before anything else">
These contracts **record**; they do not **hold**. Neither `batch_registry` nor `payout_vault` transfers a token — there is no `token::Client` in either. `fund_vault` writes an attestation that the buyer funded, and `approve_settlement` writes that they approved.

So this is a tamper-evident audit trail for a settlement, not custody of the settlement. Read [what it does and does not do](/AgriBatch_Pay/overview/scope/) before you plan anything around it.
</Aside>
